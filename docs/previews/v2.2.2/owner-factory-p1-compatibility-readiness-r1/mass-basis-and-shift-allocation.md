# 质量口径、来源与两班分配

旧字段daily_inbound_mass_kg单位kg/day，代表原果进厂量；旧定员直接消费该值。
新Q1/Q2单位kg/shift，代表包装产品质量，不是件数、箱数、原果质量或设备运行小时。
单件1.6kg属于Owner确认的包装生产率模型，不允许把未知口径输入当作已是产品kg。

正式上游来源至少需要：项目及产品/包装身份、共同生产期间、质量单位/口径、
每日及班次分配、实际源文件字节Hash、发布者/提供者、审核批准状态和版本。
只有原果量时，还缺有来源的出成率或实际质量平衡、适用批次及原果→产品关联。
若库存跨日、次果/损耗等影响关系，须显式解释，不能默认成品=原果或套未经批准比例。
本轮不计算或默认出成率，不给历史20吨自动配20000kg包装产品。

两个班次均须明确给出；只有日包装量时不默认50/50，缺第二班时不自动减出余额。
若同时提供日包装量，必须与Q1+Q2精确相等，否则拒绝，不自动修改任一输入。
N1=ceil(Q1/192)、N2=ceil(Q2/192)，不先合并取整。人数是整数，质量用精确有理数。

## 本轮实际离线来源检查

工具读取限制在指定证据根目录下的JSON文件，并核对实际字节SHA、项目/时段、kg产品口径、
两个班次质量与请求一致。绝对路径、越界路径、缺文件、伪Hash、错项目/时段和错数量均拒绝。
调用方自填verified/authoritative/authority_token不构成准入依据。

这只能证明“本地记录和所引字节一致”。任意人也能给合成文件计算真实Hash，
因此本工具无论匹配与否，都不会产生正式来源批准或Server Canonical身份。
两个synthetic源JSON只用于功能测试，明确不是真实项目输入或出成率证据。
正式系统还需可信业务入口、审核与角色权限、实际文件获取与发布者/版本核验。
不能直接把本工具的成功状态改名为正式认证PASS。

## 比较边界

LEGACY_CANONICAL重放原果20吨的原规则结果；OWNER_V1_PROPOSED独立保存显式产品质量。
本轮所有新旧面积对比均NOT_COMPARABLE；即使数字恰好相同，也不能消除语义差异。
未来批准了共同项目/时段及质量转换后，可定义专用可比性合同，仍不得把班制/功能假设变化
解释为布局算法改进。历史结果和Hash不重写。
